# 接续工作与交付记录

## 几分钟内找回现场

1. 从用户指定的工程、交接单或资料开始，查团队实际使用的记录系统。若项目留有 `.supertools/` 也可从中接续。按交付对象与接收目标筛选，按记录内的执行时间排序。复制文件会改变文件修改时间。
2. 找到相关用例，比较候选版本、目标最近一次交付尝试，以及该目标最近一次通过业务验收的版本。用可读取的安装记录、签收回执、运行状态或作业核实。若缺少现场权限，明确写“上次记录为……，当前版本待核实”。
3. 用户只问进度时，直接回答“做到哪里、证据在哪、下一步是什么”。要求继续时，从第一项尚未完成且已获授权的操作接续。仓库已有工程而交付记录缺失时，根据现有代码、测试、CI 和运维手册接手。将查不到的信息标为未知。
4. 发布结果不明，先查已有作业、接收方或目标环境。交付已完成且同一候选仅缺复验时，从实际使用入口接续该用例。源码、产物或目标已经改变时，识别受影响的检查再执行。历史的单次发布授权不能用于另一个版本或环境。

例如测试环境记录了 v2 上传成功、报价验收失败，上一个通过版本是 v1。若现场仍为 v2，向用户报告“测试环境当前运行 v2，报价检查未通过；最近验证通过的是 v1”。接着检查失败用例或按已授权的恢复请求处理。

### 当记录给出不同结论

按交付对象、环境、版本和运行模式逐项对齐证据。工程迁移查主线切换记录，公开发行查实际下载包或平台发布回执，业务验收查该版本用例的实测结果。若汇总台账和直接证据冲突，保留日期和证据位置，指出需要更正的那一项。模拟支付、备用模型或单平台测试通过时，注明覆盖的模式。完整回归中有失败断言时，同时报告已通过的子项、首个失败输入和预期，以及下一次从哪项重跑。

## 记录放在哪里

优先使用接手人能访问的工单、发布清单、签收表或项目文档。只读任务直接在回复中给出结果。团队尚无约定且需要留存时，先确定谁需要读取记录。共享说明可以放进项目文档，临时证据可保存在约定的工作目录。下面是自选本地文件布局的例子。仅保存在个人工作区的记录用于团队交接时，应在既有共享位置留下可访问的依据。

| 本地布局示例 | 可记录的内容 |
| --- | --- |
| `.supertools/runs/<run-id>.md` | 目标、版本、时间（含时区）、验收 ID、预期与实际、结果、脱敏证据 |
| `.supertools/releases/<attempt-id>.md` | 环境、实际验收入口、CI 作业链接或部署回执、候选与产物位置、摘要或不可变修订、部署结果、关联的本地及线上验收记录 |
| `.supertools/artifacts/<release-id>/site/` | 已接受的候选静态文件。保留可恢复版本，记录文件放在站点目录之外 |
| `.supertools/ops/<run-id>.md` | 时间、影响、现场版本、关键观察、采取的操作、恢复后的业务验收 |

用已有记录的条目、评论或独立文件区分各次尝试。重试、回滚和复验关联之前的结果。有 Git 时可以记录提交及工作区修改状态，有未提交改动或无 Git 时可用产物摘要、构建 ID 等区分实际候选。分别记录目标收到的版本和最近一次业务验收通过的版本。

中断或交接时，留下接手人能找到的入口和证据，例如测试命令、工单号、介质编号或作业链接。注明阻塞原因和下一项待验操作。对必要的日志、截图和地址脱敏，凭据沿用项目原有的保管方式。

例如一次可接续的发布记录可以写成下面这样。

> 测试环境 · 构建 812 · 已部署，AC-01 未完成。
>
> 验收入口 `https://staging.example.org/quote/`，构建记录 `https://ci.example.org/jobs/812`。
>
> 入口返回 503，最近一次通过验收的是构建 809。入口恢复后，先核实线上版本，再对 812 重跑 AC-01。
