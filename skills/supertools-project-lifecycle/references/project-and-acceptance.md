# 建项、开发交接与验收

## 从想法开始

先落实用户、交付目标和第一条能实际检查的成功标准。只在影响第一版方案时，追问多人共享、登录权限、私密服务调用等需求。给出适合当前需求的技术选择和理由。创建工程前核对目的目录；发现已有文件时先识别工程。按已授权范围生成最小可运行工程，在当前环境实际打开预览或运行入口。

沿用项目记录目标与验收条件的方式，例如 README、需求工单或团队签收表。需要新建说明时，可按项目语言裁剪随包模板。先写已有信息，让后来的人能用同一个名称、工单号或验收 ID 找到用例。交付渠道尚未决定时，可先实现并验证第一个本地用例。

## 接手已有工程

从当前可读材料找出目标组件、工作目录、运行环境和验证入口。有构建清单、锁文件或流水线时，以生效配置为线索。有的工程仅提供脚本、设备或操作手册，此时按其记载的入口工作。多组件工程结合用户提及的功能和改动范围定位目标。保留现有目录、脚本与未提交改动。

用户要实现功能时，从约定的用户操作出发，完成一个可以实际运行的改动，用下方步骤验收。用户要写交接任务时，把“在哪里改、改什么、用哪一条验收、已知失败怎样复现”整理成一段可复制的任务。

## 做一次可重复的验收

1. 确认输入、预期结果、检查方法和目标版本。网页可检查一次浏览器交互，CLI 可运行一个业务命令并核对输出和退出码，库可从消费方导入并调用，设备可按手册操作并记录观察者。需要临时启动服务时，核对端口与实际应用，结束后只回收本次启动的进程。
2. 验证发布候选时，使用拟交付的产物和相应配置。接收方复验沿用同一条业务用例、预期值和该环境允许的测试数据。人工项注明谁在什么版本观察到了什么。
3. 使用项目已有的状态名称，区分实测通过、观察到失败和条件不足尚未验证。权限或工具缺失导致无法运行时，注明缺项。若验收条件本身就是可访问性，已确认的停机就是失败。
4. 失败后记录最早可复现的步骤、预期和实际差异。修复或交接后，对新候选重跑原用例，保留原版本记录。若需求发生变化，记录验收条件的修订，再判断哪些结果需要重验。

例如 `AC-01` 要求在页面输入单价 100、数量 2 和九折后，读到应付金额 180.00。读到 200.00 属于失败；测试账号过期导致无法进入报价页，则这次金额检查未完成。
