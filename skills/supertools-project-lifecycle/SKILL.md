# Supertools 项目交付

使用用户的语言和项目已有术语。从用户指定的阶段进入。先找出谁会收到什么、怎样使用它、如何判断成功，再从当前项目说明、配置、交接记录或用户提供的材料中确认实际入口。一个任务可以跨多个阶段，也可以只做一次本地验收或进度查询。

| 用户可能会说 | 从哪里开始 | 本次应交付什么 |
| --- | --- | --- |
| “我想做一个报价页，帮我建项” | [建项与开发交接](references/project-and-acceptance.md)，按需使用[通用模板](assets/delivery.md) | 可运行的第一步、一条能实际检查的成功标准 |
| “把这个功能做完，在本地验一下” | [开发与本地验收](references/project-and-acceptance.md) | 可运行的改动和同一条业务用例的实测结果 |
| “接手这个项目，帮我验一下这次改动” | [本地验收](references/project-and-acceptance.md) | 实际测试的版本、观察到的结果，失败时附复现方式 |
| “上次做到哪了？”或“接着上次做” | [查找交付记录](references/records.md) | 当前阶段、最近证据和下一步；要求继续时执行已获授权的下一步 |
| “准备上线”“发布这个包”或“交给客户离线安装” | [发布与交付复验](references/release.md) | 准备时给出候选、目标与缺项。执行后给出实际到达目标的版本和业务复验结果 |
| “服务打不开了”“安装后不能用”或“恢复上一版” | [按需巡检与恢复](references/operations.md) | 影响范围、现场观察，实施恢复后给出版本和业务复验结果 |

**沿用项目约定。** 按用户指定的技术栈、操作系统、测试方法、发布渠道和记录位置工作，未指定时从现有工程查证。只有新项目确实需要选型时，才给出满足首条验收条件的最小方案并说明假设。缺少的信息会改变交付内容、目标或权限时再询问。

**按交付对象验收。** 一次改版可能包含网页、服务、命令行工具、库或安装包。分别从各自的使用入口验证，沿用现有测试、工单、运行手册和签收流程。需要新建交付说明时，可裁剪[通用模板](assets/delivery.md)。

**按任务范围执行。** 进度查询和巡检从只读检查开始。写文件、运行项目生命周期命令、发布和恢复需有覆盖该操作的明确授权，复用本次任务已有授权。工具按环境选用，可读取本地文件、现有 CLI 或已配置的 MCP，也可核对用户提供的回执。目标不可访问时，注明已验证范围与待核项。

**可选的静态目录工具。** 项目采用 CloudBase 静态托管时，可参考[直接上传与恢复示例](references/cloudbase.md)。该示例使用的[目录指纹脚本](scripts/artifact-fingerprint.ts)需要 Node.js 22.6+。项目已有可信摘要、签名或不可变构建编号时沿用其校验方式。

**以用户看到的结果收尾。** 说明在哪个环境、对哪个版本做了什么验证，给出证据和仍待解决的具体事项。发生中断时，把失败的步骤、输入和接续位置留在[交付记录](references/records.md)里。
